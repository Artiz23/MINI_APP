# SESSION HANDOFF — только MINI_APP

Этот документ описывает исключительно Telegram Mini App из `MINI_APP/`: его функциональность, backend, интерфейс, Telegram-интеграцию, данные, проверки и развёртывание. Работа над другими ботами проекта сюда не входит.

## Цель и договорённости

Доработать Telegram Mini App по `MINI_APP/PLAN.md` и последующим уточнениям пользователя. Каталог приложения — `E:\TG_BOT_ORH3\MINI_APP`. Команды сборки выполняются из `E:\TG_BOT_ORH3` в PowerShell, поскольку приложение использует общий Go-модуль.

Пользователь предпочитает короткие отчёты и готовые команды. Он самостоятельно обновляет Mini App на Debian-сервере через SCP. В этой сессии агент не подключался к production.

## Актуальное состояние на 7 октября 2026

План из `MINI_APP/PLAN.md` реализован и проверен. По решению владельца прибыль вводится сотрудником вручную как сумма и валюта, без формулы и FX-пересчёта. Отрицательная сумма означает убыток.

Production-сервер не обновлялся. Пользователь сам загружает файлы по SCP и перезапускает systemd-службу.

Последние исправления интерфейса: кнопки «Согласование», «Оплата», «Ещё задача» и «Обращение» больше не блокируются без объяснения. «Согласование» у открытой заявки автоматически переводит её в работу; преждевременное нажатие следующего действия показывает обязательный текущий этап. Группы согласования, оплаты и сальдо выбираются из групп, заранее созданных в разделе «Чаты»; произвольный ID сервер отклоняет. Backend по-прежнему соблюдает строгую последовательность. Текущая версия фронтенда — `v98`: каждая валюта ЦБ и пара ProFinance выводится отдельной строкой.

## Что реализовано

- Миграции JSON со `schema_version = 2`, автоматической резервной копией перед миграцией и предупреждениями о неизвестных legacy-значениях.
- Заявки «Мои / Все», серверная проверка прав и режим только для чтения для чужих заявок операциониста.
- Статусы `open → in_progress → success_closed | failed`; причина обязательна для `failed`; повторное открытие доступно администратору с причиной.
- Строгие этапы согласование → оплата → задача → обращение → завершение; администратор может пропустить этап с причиной.
- Отдельный редактируемый комментарий, структурированная экономика сделки, ручная прибыль и справочник агентов.
- Канонический баланс сальдо и журнал операций; контрагента с финансовой историей удалить нельзя.
- Раздельные настройки Telegram-чатов согласования, оплаты и сальдо. Согласование отправляет заявку и сальдо одним сообщением с inline-кнопками «Принять», «Отклонить», «Спор». Решения доступны администраторам; спор создаётся в разделе согласований. CSV отдельно не отправляется. Повтор доставки не дублирует успешно отправленное сообщение.
- Клиентский флаг комиссии и идемпотентное автоматическое напоминание после успешного закрытия заявки.
- Встречи с HTTP/HTTPS-ссылкой и временем по Москве.
- Три настраиваемых слота курсов. Курсы находятся в нижней панели, Канбан остаётся в общем меню.
- Ежемесячный ZIP-снимок выбранных разделов вручную и по расписанию, без дублей за месяц.
- Activity heartbeat и аналитика по сущностям и периодам: заявки, конверсия, продажи, фиксированные комиссии и активность. Показатели разделены по валютам.
- Telegram initData отклоняется, если старше 24 часов или имеет `auth_date` более чем на 5 минут в будущем.
- `MINIAPP_BOT_TOKEN` читается из окружения. Linux unit подключает `/root/miniapp/.env` через `EnvironmentFile`.

## Прибыль и процентные комиссии

Прибыль берётся из ручного поля заявки и в аналитике суммируется по успешно закрытым заявкам отдельно по валютам. Процентные комиссии сохраняются как условия сделки, но автоматически не рассчитываются — это согласованное упрощение, а не незавершённая задача.

## Последняя задача: сообщение заявки в Telegram

Пользователь хочет одно сообщение по образцу:

```text
🆕 Заявка №69
👤 Менеджер: Da REX (@damirexxx)

2 227 000р ~ 26 626 юсдт
Интермар → Крафты
➡️Отправляем 2 227 000р
💰Получаем 26 626 юсдт (ТОД)

Сальдо:
Нерезидентский рубль: 2 344 500 RUB
SWIFT: 217 008 CNY, 298 879 EUR, 44 000 USD
```

Реализовано: жирный заголовок HTML, UID заявки, имя менеджера из справочника (fallback — имя отправителя), комментарий заявки с переносами (fallback — Title), snapshot сальдо контрагента. Сальдо сгруппировано по `KindLabel`, валюты внутри типа разделены запятой. Суммы и текст условий не выводятся автоматически из экономики — сотрудник пишет их в комментарии. Username менеджера отдельно в модели отсутствует: появится только если включён в имя. Заголовок сейчас `🆕 Заявка <UID>` без принудительного символа №. Разделители тысяч в snapshot сальдо автоматически не добавляются.

Inline callback data: `apr:approved:<id>`, `apr:rejected:<id>`, `apr:dispute:<id>`. Обработчик проверяет администратора/владельца и совпадение группы и message ID с сохранённым согласованием. Принять/отклонить вызывают `DecideApproval`, затем редактируют текст сообщения, добавляя результат и имя. Спор создаётся через `AddDispute("approvals", UID, ...)`, дальнейшее обсуждение — в Mini App.

## Следующие шаги и известные проблемы

1. Пользователь должен загрузить актуальные Linux binary и web на сервер и открыть Mini App заново. Он признал, что скриншот с курсами через `·` был сделан до обновления; это не подтверждение неисправности `v98`.
2. Проверить в настоящей группе: создание одного сообщения, принятие, отклонение, открытие спора, права обычного сотрудника и продвижение workflow. Production-проверок пока нет.
3. При необходимости довести точное оформление образца: символ №, username менеджера и формат тысяч. Сейчас эти элементы не полностью автоматизированы.
4. «Спор» можно нажимать повторно: защита от создания нескольких одинаковых споров пока не добавлена. `AddDispute` в существующем коде игнорирует ошибку сохранения.
5. Ошибка редактирования Telegram-сообщения после решения сейчас игнорируется. Решение сохранится в базе, но карточка в группе может остаться визуально старой. Решение из Mini App не синхронизирует автоматически текст и кнопки уже отправленной карточки в группе.
6. Одно Telegram-сообщение ограничено длиной; проверки/сокращения длинного комментария вместе с сальдо пока нет. Если Telegram отклонит отправку, запись доставки получит ошибку.
7. Legacy-доставка: частично отправленные старые согласования с `DeliveryParts` могут быть помечены доставленными без пересоздания карточки с кнопками. Старые сообщения не обновляются автоматически.
8. В `approval_delivery.go` остались недостижимые ветки отправки отдельного сальдо/CSV (`case 1/2`), поскольку теперь `parts = 1`; их можно удалить при следующей правке. CSV snapshot пока сохраняется в данных, но отдельно не отправляется.
9. Временная папка `.miniapp-test-tmp` после последнего Go-теста может существовать. Удалять только после проверки точного абсолютного пути внутри проекта.

## Технические детали и запуск проверок

Зависимость сборки Mini App: корневые `go.mod`, `go.sum` и импортируемые общие пакеты `internal/`. Это техническая зависимость приложения; перенос Mini App в отдельный самостоятельный Go-модуль не выполнялся.

Go backend и vanilla JS/CSS, без npm-сборки. JSON хранится в `data/miniapp.json`, вложения — в `data/files`. Store использует mutex и запись через временный файл + rename; не вызывать публичные методы, повторно захватывающие mutex, из `*Locked` методов. Новые денежные поля — decimal-строки, точное суммирование через `math/big.Rat`; legacy-суммы местами остаются float64.

API использует заголовок `X-Telegram-Init-Data`, HMAC и срок auth_date. `navSeq`, `bumpNav()` и `alive(token)` предотвращают устаревшие перерисовки. Ручная прибыль редактируется только в открытой заявке/в работе; аналитика включает её по успешно закрытым заявкам, сгруппированным по дате создания заявки и валюте.

В Windows sandbox системный TEMP давал `Access is denied` на rename. Для тестов создать `.miniapp-test-tmp` внутри проекта и назначить TMP/TEMP на него. Для Playwright доступен установленный Edge, а не bundled Chromium; запуск браузера требовал escalation.

```powershell

$env:TEMP = $env:TMP
New-Item -ItemType Directory -Force $env:TMP | Out-Null
go test ./MINI_APP/... -timeout 60s

$env:NODE_PATH = 'C:\Users\arty\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\node_modules'
$env:BROWSER_EXECUTABLE = 'C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe'
node --test MINI_APP/tests/archive-ui.test.cjs
```

Сборка Linux из корня:

```powershell
$env:CGO_ENABLED = '0'
$env:GOOS = 'linux'
$env:GOARCH = 'amd64'
go build -o MINI_APP/dist/linux/miniapp ./MINI_APP/cmd/miniapp
```

Перед перезаписью работающего Linux-бинарника остановить службу. Сохранить всю папку данных. После загрузки выполнить `chmod +x /root/miniapp/miniapp`, запустить службу и посмотреть status/journalctl. Для обновления только интерфейса достаточно загрузить все три web-файла и переоткрыть Mini App. Изменение `.env` требует restart, но не пересборки.
